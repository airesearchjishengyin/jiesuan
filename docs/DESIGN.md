# 借算 (Jiesuan) · 边缘算力共享管理框架 — v0.1 设计方案

日期: 2026-09-09 · 状态: 待审阅 · 作者: Hermes (代拟) + Jisheng Yin
定位: **面向 agent 推理的边缘设备算力收集框架** — 内网部署优先, 开源发布, 学术/商业双轨共用一套代码。

---

## 0. 一句话

> 把局域网内的闲置 Mac/PC 组成一个**内存常驻的 agent 推理池**: 一个 API 入口, 多台机器按策略分摊专家计算; 时序预测器作为高级调度层后置接入, 不阻塞商用基础版。

## 1. 背景与动机 (为什么是现在)

1. **需求侧**: agent 推理占总计算 70%+ (巴克莱 2026), 推理需求 4.5-10× 训练; agent 负载天然"多请求、小模型、延迟敏感" — 与"单机独占跑大模型"完全不同的资源形态。
2. **供给侧**: 企业/实验室/工作室内大量 MacBook 岗位闲置率 >60%, GPU/M-series 芯片闲时浪费; 国内无任何面向 agent 推理的个人/内网算力共享方案 (算了么=离线批处理且停更, 共绩科技已转企业市场, GPUsMarket=海外+Stripe 壁垒)。
3. **技术侧**: MoE 推理的稀疏激活 (A3B 级每 token 仅 ~3MB 激活流量) 使"专家分布式驻留+激活路由"在千兆内网完全可行 (1:476 的流量比); slotstream 的 ExpertStore + 我们的 router-trace 是现成的技术底座。

## 2. 核心设计决策 (D1-D5, 请重点审阅)

### D1 · 双轨分层: 内存常驻为基座, 预测器为插件

```
┌─────────────────────────────────────────────────────┐
│                 Scheduler Layer (可插拔)              │
│   L0: RoundRobin(默认)  L1: 负载感知  L2: Temporal   │
│        ↑ L0/L1 = 商业线(v0.x 交付)                    │
│        ↑ L2 = 学术线(预测器, 后置接入)                │
├─────────────────────────────────────────────────────┤
│              Router Layer (模型路由)                  │
│   请求→节点分配: 全驻留池内直接路由, 无需流式          │
├─────────────────────────────────────────────────────┤
│           Node Layer (节点抽象, 统一三层)              │
│   节点 = {engine(ollama/llama.cpp), capacity, health}│
│   节点内部自主决定 VRAM/RAM/SSD 驻留 — 对上层透明      │
├─────────────────────────────────────────────────────┤
│              Transport Layer                          │
│   内网: mDNS 发现 + WebSocket + HTTP(OpenAI 兼容)     │
└─────────────────────────────────────────────────────┘
```

**内存常驻 vs 预测器的适用边界** (依据: 比值定律 0.33×→137t/s, 5×→1t/s):

| 模型 | 单副本 | 3台池(24GB) | 5台池(40GB) | 常驻可行性 |
|---|---|---|---|---|
| qwen3:8b (Q4) | 5.5GB | ✅ 全驻留 | ✅ | 商用线目标场景 |
| qwen3:14b (Q4) | 9.3GB | ✅ (1/台) | ✅ | 商用线目标场景 |
| 32B 级 (Q3) | ~15GB | ❌ | ✅ (3台拆分) | 学术线用武之地 |
| 100B+ (Q4) | 105GB | ❌ | ❌ | 预测器+流式的战场 |

**结论**: 内网场景的 agent 负载 (7B-14B 级) 用常驻方案完全覆盖; >池容量的模型才需要预测器+流式 — 所以**商业线不依赖学术线**, 学术线作为 L2 调度插件后置接入。

### D2 · 三种部署模式 (同一二进制, 配置切换)

```bash
jiesuan --mode solo      # 单机模式: 本机引擎+API网关 (家庭/开发者, 传播入口)
jiesuan --mode pool      # 内网池: mDNS发现+多机调度 (实验室/企业内部, ★核心场景)
jiesuan --mode network   # 跨网网络: 志愿节点+Nostr身份 (社区/学术, v1.0+)
```

- `solo`/`pool` 模式流量不出内网 → **无 ICP/内容监管问题** (非经营性内网部署)
- `network` 模式开源代码、自部署、无中心服务 → 责任在部署者 (exo/Petals 先例)
- **永不内建支付/撮合/抽成** — 计量数据内建(企业成本分摊要用), 结算留给部署者

### D3 · OpenAI 兼容 API 是唯一对外接口

```
POST /v1/chat/completions  →  网关按策略路由到节点  →  流式返回
```
- 任何 agent 框架 (Hermes/LangChain/Cline/OpenCode) 零改动接入
- 兼容性=采用量的前提, 不自造协议

### D4 · 技术栈: Python + asyncio (你的主场) + Swift/ObjC 最小壳 (Mac 常驻)

| 组件 | 语言 | 理由 |
|---|---|---|
| 网关/调度/路由 | Python (asyncio) | 你最熟, 高并发 IO 密集=asyncio 主场, 论文实验也用它 |
| 节点 agent | Python + launchd/systemd | 跨 Mac/Linux; 电源管理用系统 API |
| Mac 菜单栏壳 | Swift (可选, v0.5) | 用户体验; v0.1 用 CLI 即可 |
| 计量/报表 | SQLite + 简单 Web | 内网用, 不需要重型栈 |

### D5 · 红线 (安全与合规)

1. **永不内建支付/撮合** — 计量可以, 结算不行 (避开二清/帮信暴露面)
2. **默认内网** — network 模式需显式开启 + 显示隐私警告
3. **prompt 不落盘** (除非部署者开启审计模式)
4. **开源协议**: Apache-2.0 (企业友好, 便于将来 Enterprise 版)

## 6. 风险与开放问题 (请审阅时重点标注)

1. **Ollama 模型放置的粒度**: 池内多节点跑同一模型 (冗余) vs 拆分跑不同层? v0.1 选前者 (简单可靠), 拆分留 v1.0
2. **Mac 睡眠策略**: 合盖场景依赖 BetterDisplay 虚拟屏 (已验证) — 企业部署时 IT 管理策略如何统一? (MDM 推配置?)
3. **多租户隔离**: v0.1 不做 (内网信任域); 企业场景若需要, 走 Enterprise 功能
4. **Windows 节点**: v0.1 只支持 macOS; Windows 经 WSL2 理论可行, 优先级低
5. **命名**: "借算" (Jiesuan) 仅占位, 开源发布名可再议 (备选: AnyOffer / MacPool / EdgeMesh)
